# Skills Market Hub

**DeepSeek Harness 的技能市场插件**：在桌面端侧栏浏览 ClawHub 与 SkillHub 上的技能，读说明、看文件、确认后安装到本机，并在同一个面板里管理已安装的技能。

当前版本 **0.1.9**（[更新说明](./CHANGELOG.md)）。已在 DeepSeek Harness `0.2.0-rc.2` 上实测运行，见[验收记录](#验收记录)。

本插件是独立的社区项目。技能由各自的作者发布，版权归原作者，以每个技能自己声明的许可证为准；本仓库的 MIT 许可证只覆盖插件自身的代码。

## 这个插件做什么

| 功能 | 说明 |
| --- | --- |
| **发现页（默认）** | 五个榜单：精选、热门、官方、新发布、装机最多，每栏最多 10 条，一栏一行、右侧显示该栏排名所依据的那个数字；每栏底部可跳转到「市场」继续找 |
| **双源浏览** | ClawHub 与 SkillHub 同时检索，跨源镜像自动折叠（保留原始条目，不展示过期的副本） |
| **分类标签** | 卡片与详情显示注册表的分类（SkillHub 的细分项与顶层分类、ClawHub 的 `categories`），按界面语言取上游发布的中文或英文名，解析不出来时退回稳定 key |
| **热度两个维度** | 卡片同时显示下载量与收藏量 —— 前者是取走副本的人，后者是留下来的人 |
| **筛选与搜索** | 市场按来源、安全结论、安装状态筛选；已安装列表按来源筛选；两处的关键词搜索都对全角/半角与 markdown 强调符号做归一化 |
| **安装前预览** | 完整 SKILL.md、逐文件清单与内容、上游安全报告、版本变更日志 |
| **确认后安装** | 弹窗列出来源、作者、版本、安全结论；勾选知晓后才可确认 |
| **已安装管理** | 列出本机全部技能（含手动放入的），每行标明来源注册表与「市场安装/本地」，可预览、可卸载 |
| **持久快照** | 上游数据落盘缓存（默认 60 分钟），`fetchedAt` 命中不重新盖章，上游不可用时回退陈旧数据 |

### 「发现」的五个榜单各是什么

榜单不是编辑挑选，是**对注册表已公布数字的排序**，每一栏的规则都写在界面提示里：

| 榜单 | 依据 | 数据来源 |
| --- | --- | --- |
| 精选 | 在「下载 / 安装 / 收藏」三个排序里都靠前，**进两个才算**，先按进榜数、再按最好名次 | 本插件对已公布数字的汇总 |
| 热门 | ClawHub 发布的 `trending` 索引；SkillHub 无排序参数，按其**安装量**排列；两边**交替**展示 | ClawHub 索引 + SkillHub 列表页 |
| 官方 | 注册表自己标为已认证（`verified`） | SkillHub 列表的 `verified` |
| 新发布 | ClawHub 发布的 `newest` 索引；SkillHub 按最后更新时间排列；两边交替展示 | ClawHub 索引 + SkillHub 列表页 |
| 装机最多 | 注册表公布的安装量 | 两个注册表 |

**官方这一栏常常很短甚至为空，这是事实而不是缺陷。** 两个注册表都极少给出认证标记：SkillHub 首页约百中有一，而 ClawHub 只在**搜索**接口声明 `official`／`featured`，它的列表接口（本插件浏览用的那个）完全不返回该字段，也没有任何可以枚举官方发布者的端点（`/publishers`、`/official`、`sort=official` 全部 404 或 400，已实测）。所以这一栏只用能观察到的信号，不用近似条目凑数 —— 空的时候界面会说明原因。

`sort` 的取值也是实测出来的：`downloads`／`installs`／`stars`／`trending`／`newest`／`updated` 返回 200，而拼错的（`recent`、`featured`、`official`）返回 **400 而不是回退到默认排序** —— 所以映射表是封闭的，不是一个拼字符串的模板。

## 安装

```bash
dsh plugin --profile desktop add <本包路径或包名> -w
```

装完重启 DeepSeek Harness 桌面端，侧栏会出现「技能市场」入口。

本插件只向 profile 的插件行**插入自己一行**，不替换任何官方组件。想移除时删掉那一行即可。

### 修改代码后，profile 需要重新安装一次

**这是最容易踩的一个坑**：用 `file:` 指向本地目录安装时，包管理器放进 profile 的不是软链接，而是**安装那一刻的拷贝**。之后你改源码、重新构建，profile 里仍然是旧版本 —— 而插件"看起来装好了"，所以这个现象很难归因：你复现的仍然是已经修好的那个错误。

从 0.1.2 起，插件会**自己发现这件事**。宿主的日志里会出现一行：

```
skills-market-hub: ready (v0.1.2, root=…, install=…, uninstall=on, cache=60m)
```

如果加载的构建与它旁边的 `package.json` 版本不一致，紧跟一条警告，写明两个版本号和要执行的命令。

每次改完代码、重新 `pnpm build` 之后：

```bash
cd ~/.dsh/profiles/desktop
pnpm install --force --no-frozen-lockfile
```

然后重启桌面端。

`--force` 不能省：包管理器按 `file:` 路径缓存依赖，不加它就会认为"路径没变，无需处理"，拷贝依旧是旧的。

> 试过用 `postinstall` 钩子自动重建，**已放弃**：pnpm 11+ 默认拦截依赖的 install 脚本，那样会让**整个 profile 安装失败**（`ERR_PNPM_IGNORED_BUILDS`）。为了省一步手工操作而弄坏主要安装流程，不划算。所以这里选择"发现并说清楚"，而不是"自动修"。

判断 profile 里到底是哪一份，直接比哈希（PowerShell，两边应输出同一个值）：

```powershell
Get-FileHash "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\dsh-skills-market-hub\package.json" -Algorithm SHA256
Get-FileHash "D:\projects\dsh\dsh-skills-market-hub\package.json" -Algorithm SHA256
```

包的版本号也能直接看出来（Windows 上 `require()` 会被反斜杠路径绊住，所以这里读文件再解析）：

```powershell
node -e "console.log(JSON.parse(require('fs').readFileSync(process.env.USERPROFILE+'/.dsh/profiles/desktop/node_modules/dsh-skills-market-hub/package.json','utf8')).version)"
```

改代码时不建议改用 `git+ssh://…` 安装：那条路走的是仓库里提交的 `lib/`，每次改动都要先提交推送再重新拉取，联调阶段反而更慢。等插件稳定、或要部署到别的机器时再换。

### 从源码构建

## 配置

写在 profile 的插件行 `config` 里；每个字段都有默认值，写 `{}` 也能启动。

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `skillsRoot` | `null` | 安装到哪个目录。`null` = `$DSH_HOME/skills` |
| `clawhubBaseUrl` | `https://clawhub.ai` | ClawHub 地址 |
| `skillhubBaseUrl` | `https://api.skillhub.cn` | SkillHub 地址 |
| `timeoutMs` | `15000` | 单次上游请求超时 |
| `requestRetries` | `1` | 首次失败后的额外尝试次数（仅对 429 与 5xx 重试） |
| `allowUninstall` | `true` | 是否允许卸载。关掉后卸载端点一律 405 |
| `pageSize` | `24` | 列表默认页大小（1–100） |
| `cacheTtlMinutes` | `60` | 上游快照有效期（1–1440） |

## HTTP 接口

一条前缀路由 `/api/skills-market-hub`，全部返回 JSON 且 `Cache-Control: no-store`；失败恒为 `{ error: { code, message } }`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/ping` `/version` `/stats` `/status` | 存活、版本、缓存计数、逐源健康 |
| GET | `/discover` | 发现页：五个榜单（`{ id, metric, items }`）与逐源健康。参数 `refresh` |
| GET | `/categories` | 注册表发布的分类词汇表（key、中文名、英文名、排序） |
| GET | `/skills` | 列表。参数 `q, source, security, installed, cursor, limit, refresh` |
| GET | `/skills/:source/:slug` | 详情。参数 `owner`（ClawHub 的 slug 跨作者共享时必填）、`refresh` |
| GET | `/skills/:source/:slug/file` | 单个文件内容。参数 `path`（必填）、`owner` |
| POST | `/install` | body `{ id: "source:slug", owner? }` |
| POST | `/uninstall` | body `{ id }` |
| GET | `/installed` | 本机技能清单 |
| GET | `/installed/detail` | 单个已安装技能的文档与文件清单。参数 `key` |
| GET | `/installed/file` | 已安装技能的单个文件。参数 `key`、`path` |
| POST | `/installed/uninstall` | body `{ key }` |

`key` 是技能绝对路径的 SHA-256：浏览器端从不持有真实路径，主机端每次请求用这个 key 重新扫描磁盘来解析，所以调用方无法构造出任意文件读取。

## 设计约束

这几条不是风格偏好，是**发布形态强加的**，改代码前值得先读：

**运行时零依赖。** 宿主以「装好但未构建」的形态加载插件，未被提升到 profile 里的依赖会让插件加载失败。因此 YAML frontmatter 由自带的子集解析器处理（支持块标量、流式集合、引号转义），Markdown 不引入渲染库。

**客户端产物只依赖 React。** `lib/client.cjs` 里出现的每一个 `require()` 都必须是平台种子模块。共享的 UI 原语包（`dsh-client-ui-primitives`）被**刻意不使用**：它的入口在顶层静态导入 katex、shiki、mermaid 语言包、`simple-icons` 与三十余个样式表，取它一个按钮等于把这些全部打进本插件的 bundle。面板因此自己用 `--dsw-*` 主题 token 画控件，代价是零。

**客户端产物是 `.cjs`。** 主机半是 ESM（与其他 DSH 插件一致），而给浏览器模块加载器的产物是 CommonJS 闭包工厂。用扩展名表达这个差异，而不是在 `lib/` 里放一个 `package.json` —— 那会连主机半一起声明成 CommonJS 并让 `import` 直接报错。构建脚本会断言 `lib/` 下不存在那个文件。

**信任门每次请求解析。** 原始 web 路由不继承 Connection 服务的 Host/Origin 围栏，而 Connection 行可能晚于本插件激活；快照会让市场在围栏就位前对任意网页可读可装。

**安装不信缓存。** 详情与文件清单在写入磁盘前强制 `force: true, allowStale: false`；每一个上游给出校验和的文件都会现场比对，不匹配即中止，暂存目录整体丢弃。

**落盘只走原子发布。** 文件先写进**技能根同级**的工作目录（`.skills-market-hub-work`），全部校验通过后一次 `rename` 发布。卸载先 `rename` 到同一个工作目录再删除。同级是关键：同一卷，所以 `rename` 保持原子（跨卷会退化成复制+删除）。这一步在 Windows 上会被杀毒/索引/同步工具的短暂句柄挡住（`EPERM`，这个错误码名字有误导性 —— 不是权限问题），所以是**有界重试 + 退避**，而不是一次就放弃；清理失败也不会被吞掉，而是记进日志并在下次激活时重试清扫。

> **被扫描的目录里只放技能 —— 这不是整洁问题，是能不能启动的问题。** DSH 发现技能时会遍历技能根的**每一个目录条目**并解析 `<条目>/SKILL.md`，且**只容忍 `ENOENT`/`ENOTDIR`**；其他错误码会冒泡成 `fatal load failure`，桌面端直接起不来。0.1.5 及更早把暂存目录放在技能根内部，理由是"点前缀会被忽略"——**这个理由是错的**：点前缀骗得过按名字过滤的扫描，骗不过按路径解析的扫描。一次清理失败留下的 `EPERM` 目录就足以让整个 harness 无法启动，并让**所有**用户技能从 `/` 菜单消失。0.1.6 起工作目录移到同级；老版本留下的残留会在启动时被优先清掉。

**卸载需要自证所有权。** 目录里必须存在本插件写的 `.skills-market-hub.json`，且其中 `id` 与调用方所指的技能一致。所有权只看身份字段，账本损坏不影响归属判定 —— 但手工放入的技能永远不会被删。

### 测试

```bash
pnpm check                            # typecheck + build + 契约校验 + 360 项测试 + 打包闭包
node --test tests/*.test.mjs          # 全部离线测试
SMH_LIVE=1 node --test tests/live-providers.test.mjs   # 真实上游集成（需联网）
node scripts/capture-fixtures.mjs     # 重新抓取上游响应夹具
node scripts/pack-check.mjs           # 打包产物装进空目录后是否还能加载
```

上游响应夹具（`tests/fixtures/market/`）由真实注册表抓取，provider 归一化测试全部对着它们跑。夹具的内容会随上游变化（下载计数、首页排名），所以**断言从夹具推导，不写死字面量** —— 重新抓取后仍然应该全绿，除非上游真的改了字段名。

这条规则不是空话：0.1.3 重新抓取时，两个断言立刻红了 —— 一个把 ClawHub 的下载数写成 `50487`，另一个断言 SkillHub 列表的 `tags`「恒为 null」，而新抓到的页面里它是有值的数组。两条都是**读天气而不是读代码**的断言。

另有几条测试刻意不碰网络但也不放过路由错误：`market-service.test.mjs` 把 skillhub 的基址指向本地 HTTP 服务器，断言分类词汇表请求的**具体路径**与解析结果。起因是真实缺陷 —— 猜错路径（`/api/categories`）得到的是 405 空响应，与"上游没发布分类"无法区分，单元测试全绿而 live 测试失败。

真实上游集成测试**默认跳过**，因为它需要网络、比其余测试慢，而且上游故障不该被读成这个插件的回归。发版前跑一次：夹具是照片，它证明归一化匹配某个时刻抓到的形状，不证明注册表今天仍然这样回答。

## 已知边界

- 面板不渲染 Markdown：`description` 按作者所写的预格式文本展示。共享的 Markdown 渲染器会把整个 UI 原语包拖进 bundle（见上文），而自带一个 Markdown 子集解析器再声称它忠实还原，比直接展示原文更糟。「文件」页给出带 frontmatter 的完整源文。
- **发现页没有随包发布的策展目录，五个榜单都是对注册表已公布数字的排序。** 「精选」是三个排序的共识汇总（进两个才上榜），不是编辑挑选；界面提示里写明了这一点，因为它决定读者该不该信这一栏。
- **「官方」这一栏的信号来自注册表，不是本插件的判断，而且两个注册表都极少给出。** SkillHub 的列表接口有 `verified` 字段（首页约百中有一），ClawHub 的 `official`／`featured` 只在**搜索**结果里出现，列表接口完全不返回，也没有任何可以枚举官方发布者的端点。因此这一栏常常很短甚至为空 —— 界面会说明原因，不用近似条目凑数。
- **发现页首屏的瓶颈是 ClawHub 的服务端延迟，不是数据量**（实测 39KB 与 30KB 耗时几乎一样：1.2s vs 1.29s），所以调小 `limit` 不省时间，没有做。`trending` 与 `newest` 本来就并行，砍掉一个也不影响墙钟时间（墙钟 = 最慢的那个）。词表（1.5KB）原本串行排在三个列表前面，现改为插件激活时预热，首屏不再付这一趟。
- **发现页的三个上游页走磁盘缓存**（与详情、文件同一套 TTL）。侧栏一次只挂载一个面板，切走再切回就会重读一次 —— 实测热 1.3s、冷 4.1s，缓存命中则只是一次文件读取。**排序与安装态标注刻意留在缓存之外**：安装态是这台机器磁盘的事实，缓存成品榜单会让读者看到一栏仍在提供「安装」的、他刚装过的技能。点「刷新」会带 `refresh=1` 强制回上游。任何一页失败只损失它自己带来的条目，`sources` 会跟着榜单一起返回，界面据此说明某一栏为什么偏短。
- 没有随包发布的策展目录：列表即实时结果。因此首屏依赖上游可用性（发现页与市场都给出重试，而不是空白页）。
- ClawHub 的 slug 跨作者共享。不带 `owner` 的详情请求在上游有歧义时返回 409 与本插件抛出的候选作者列表；面板从卡片或详情页带上作者，从而避免装到另一个作者的字节。
- **只有 ClawHub 把 `owner` 当 pin 解析。** SkillHub 的详情路由本身已经确定账户，`owner` 参数不被上游解释，因此不做作者一致性校验 —— 做了会把本来可装的技能全部拒掉（0.1.0 的真实缺陷，见 [CHANGELOG](./CHANGELOG.md)）。两个 provider 的差别由 `pinsOwner` 显式声明，而不是靠猜。
- **SkillHub 的偏移分页在页边界会重叠一项。** 直接请求原始接口同样如此，属于上游行为，游标层无法消除；由面板按 id 去重，读者不会看到重复卡片。
- **分类来自注册表，不是本插件的判断。** 两个注册表各有一套分类法（SkillHub 13 个顶层分类 + 发布者选的细分项，ClawHub 自有一套 `categories`），**不做互相映射** —— 拼写相同只是巧合，把 `knowledge` 当成同一个概念会是伪造的对应关系。分类名只有上游发布的那两种语言；界面语言是第三种时，退回到中文或英文名，再退回 key。
- **ClawHub 的列表接口不返回分类。** 只有搜索与详情带 `native.skill.categories`。所以 ClawHub 的浏览卡片上没有分类 chip，除非该条目恰好是搜索命中的镜像（此时由 SkillHub 一侧补上 —— 见 `dedupe.ts`：只填空字段，永不覆盖原始来源已声明的值）。

### 0.1.3 — 安装失败

**环境**：同上，桌面端加载 0.1.3。

**观察到**（用户截图反馈）：安装 `ppt-generator-skill` 失败，底部提示只有一句「publishing the skill failed」，没有任何可用信息。

**排查结果**：`~/.dsh/skills` 里留下了一个 `.skills-market-hub-install-w4aJou`，且**删不掉** —— `rd`、`rm`、`chmod`、`rename` 全部 `EPERM`，而 `dir` 能列出它。这是一个被内核句柄卡住的目录。

三处缺陷，都在 0.1.4 修复：

- `rename` 发布失败时，Windows 的 `EPERM`（句柄被短暂持有）落进了兜底分支，报成通用磁盘错误
- 这个失败没有任何重试 —— 而同样的调用几十毫秒后就会成功
- 发布失败后的清理 `rm(...).catch(() => undefined)` **吞掉了自己的失败**，于是那个卡住的暂存目录留了下来，且没人知道

**复现验证**：把 `ppt-generator-skill` 装进真实技能根目录，成功、扫描可见、卸载干净。也就是说这是**间歇性**失败而非稳定失败 —— 恰好符合"句柄竞争"的判断，也说明只跑一次成功并不能证明修好了。

**未验证**：修复后的界面表现（需要重启后再试一次安装）；卡住的那一个目录在重启桌面端后是否可删。

> **⚠️ 下面这句话是错的，0.1.6 更正了它。** 当时我判断"它无害"，理由是点前缀会被扫描忽略 —— 这个判断基于一个**错误的模型**：DSH 遍历技能根的每个**目录**条目并解析 `<条目>/SKILL.md`，只容忍 `ENOENT`/`ENOTDIR`。那个卡住的目录正是因此让整个 harness 无法启动。详见 [0.1.5 条目](#015--装了的技能不出现在--菜单)。

### 0.1.5 — 装了的技能不出现在 `/` 菜单

**现象**：用户装了 `frontend-design`，打 `/` 看不到；重启后仍然看不到，`/` 菜单里**只有内置的 `office-*`**，一个用户技能都没有。

**第一次判断（错的）**：技能名与目录名不一致 —— `superdesign/` 目录里写着 `name: frontend-design`，所以该打 `/frontend-design`。这个观察本身正确（三个技能里两个如此：`ppt-generator-skill` → `/ppt-generator`），**但不是这次的原因**。

**第二次判断（对的）**：桌面端弹窗崩溃，日志给出确切机制：

```
dsh: fatal load failure: [Error: EPERM: operation not permitted,
  realpath 'C:\Users\admin\.dsh\skills\.skills-market-hub-install-w4aJou']
```

0.1.3 那次安装失败留下的暂存目录**一直在技能根里**，而且删不掉。DSH 解析它时拿到 `EPERM`，致命失败 —— 所以 `/frontend-design` 不是"没装好"，而是**整个技能发现流程被一个残留目录搞崩了**。

**在 0.1.6 修复**：工作目录移到技能根同级，被扫描的目录里只放技能。修复后实测发现流程恢复正常：

```
discovery OK -> 3 skills
   /anything-to-notebooklm   /ppt-generator   /frontend-design
```

**排查中我自己造成的二次故障（必须记录）**：为测试技能根是否可写，我在里面建了 `.probe-writable`。这**复现了同一个 bug** —— 删除失败后它成了第二个坏条目，再次让 DSH 崩溃（崩溃日志里 `realpath '...\.probe-writable'` 就是它）。**在一个已知"目录解析失败即致命"的目录里做写入测试，本身就是制造同类故障。** 这类实验只应在 `os.tmpdir()` 里做。

### 自动化覆盖对照

`pnpm check` 跑的部分与上面的手工观察是互补的，不是替代关系。截至 0.1.6：

| 层次 | 数量 | 说明 |
| --- | --- | --- |
| 离线测试 | 360 | 含对真实上游响应夹具的归一化（分类、标签、安全结论、热度）、安装/卸载生命周期（真实临时目录）、**被扫描目录只含技能的不变量**、发布失败的重试与分流、已安装筛选逻辑、控制器竞态与分页守卫、组件真实渲染、分类标签降级链、过期构建检测、**发现页五个榜单的排序规则与「一个注册表挂掉」的降级**、**发现页的缓存命中与强制刷新**、**词表读取的写入次序**、**面板级的安装目标解析（三个来源 + 两种空态）** |
| 真实上游集成 | 8 | 需联网，默认跳过；含一次真实的安装与卸载，以及分类词汇表的读取与落到卡片标签 |
| 打包闭包 | 15 | 产物装进空目录后能否独立加载 |
| 契约校验 | 14 | 清单、补丁层、客户端纯度、主题 token、版本一致性、peer 集合 |

分类这一条特别能说明两种覆盖的分工：**离线测试全绿而 live 测试失败**。单元测试手工填充词汇表，从不走网络，因此请求路径写错也照样通过；live 测试直接打真实注册表，立刻发现 `/api/categories` 返回的是 405 空响应。修好之后补了一条离线测试（把基址指向本地 HTTP 服务器并断言请求路径），让这类错误下次不必联网就能抓到 —— 手工观察发现问题、live 测试定位成因、离线测试固化防线，三步缺一不可。

发布失败这一条则是反面教材：**测试通过不等于测到了**。这些失败是竞态，无法按需制造，而第一版测试试图改全局 `node:fs/promises`，被只读的模块命名空间当场拒绝。改成显式接缝（`InstallOptions.fs`）之后才真正覆盖到 —— 一个测不下去的地方，通常说明代码缺少一个明确的边界，而不是说明它不需要测。

已安装筛选这一条是同一个道理的另一面：`renderToStaticMarkup` 不跑事件处理，静态渲染**无法**切换下拉，所以筛选逻辑那样测不到。提成纯函数 `filterInstalled` 之后就能直接驱动 —— 这不是为了测试而重构，那段逻辑本来就是那个视图里唯一有判断的地方。

**技能根不变量这一条，是整份测试里最该存在的一条。** 它断言的不是"清理做得好不好"，而是"被扫描的目录里有没有非技能条目"—— 后者决定了 harness 能不能启动。这条不变量**一直都在被违反，只是没有任何测试看着它**：所有测试都在验证**安装成功**，没有人问过**安装留下的东西会不会妨碍别人**。现在第一条测试就是它：暂存目录一旦回到技能根里，立刻失败。
